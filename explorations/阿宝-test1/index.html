§ 01

摘要

三句话带走整份报告

"Harness" 不是模型，也不是 IDE 插件，而是夹在两者之间的一层薄运行时：决定模型能调什么工具、看到什么上下文、被允许做什么、什么时候停。模型权重一样的情况下，harness 决定它"好不好用"。

三句话带走

  1. Harness = 模型 × 工具循环 × 上下文 × 权限 × Skill。权重买的是"会不会"，harness 决定"做不做得好"。
  2. 编辑策略（diff vs whole-file vs udiff）和上下文压缩，是当前各家最大的差异化战场。其他维度大家在收敛。
  3. Hooks + Skills 是新兴的"用户可编程层"。把 harness 从"框架内部参数"变成"产品交付物"。DeepInsight 自己也该有一层。
§ 02

何为 harness

从狭义到广义的边界划定

狭义：让 LLM 能调用工具、读写文件、与 shell 交互所必须的那段代码。广义：包括 prompt 模板、上下文管理、权限护栏、可观测、用户可扩展点 —— 所有让 raw model 变成"可用 agent"的机械装置。

一个最小 harness 至少包含：

  • System prompt（角色、约束、风格）
  • Tool schema 注入 + tool-use 循环（直到模型说"完成"）
  • 消息历史的截断 / 压缩 / 摘要策略
  • 错误恢复（工具失败、token 超限、模型返回非法 JSON）

"是否有 harness" 这个问题没意义 —— 任何能用的 agent 都有。真正的问题是：这一层做得多薄、还是多厚？暴露多少给用户调？

如果你的 agent 跑 30 步还在轨道上，那不是模型聪明 —— 是 harness 在每一步都拦下了发散的可能。 — 改写自资料 [3]，工具循环设计
§ 03

五大组件

把市面上能拿到 source 的 harness 放一起拆，反复出现的 5 块

01 · TOOL LOOP

工具循环

模型 → 工具调用 → 结果回灌 → 模型 → … 直到 stop_reason 为 end_turn。看似简单，魔鬼在终止判断、并行调用合并、错误回路上。

stop_reasonparallelretry
02 · CONTEXT MGR

上下文管理

历史消息怎么保留、何时压缩、压缩成什么样。主流：sliding window + 关键事件 pinned + 阶段性 summarize。1M token 不是免死金牌。

windowsummarizecache
03 · HOOKS

Hooks（钩子）

PreToolUse / PostToolUse / Stop / UserPromptSubmit 这类切面。harness 在固定生命周期点把控制权交回宿主，让"用户配的自动行为"成为可能。

PreToolUsedeterministic
04 · SKILLS / SUBAGENT

Skill / Subagent 体系

把"特定场景的最佳实践 prompt"和"独立上下文 + 工具子集的 agent"封装成一等公民。Skill 是规则集，Subagent 是隔离执行环境。

routingcomposition
05 · PERMISSIONS

权限 / 沙盒

tool 是否需要确认、文件能不能写、shell 命令能不能跑、敏感目录禁触。从交互式 prompt 到 allowlist 配置到 hook 拦截，由浅入深三层。

allowlistsandbox

组件之间的耦合

真正难的是组件之间的串接：hook 拦下一次写入 → tool loop 要不要把这次失败计入 stop 条件？context manager 压缩历史 → skill 注入的指令被压没了怎么办？这些边角是各家 harness 真正的工程量。

§ 05

反模式

从公开 issue 与故障 retro 里归纳的高频踩坑

A1

Tool loop 无 stop guard

"模型一直在调工具不肯停"

没有显式步数预算 + 进度判断，模型可能陷入"再 grep 一次"的死循环。修复：每 N 步注入"是否已收集到足够信息"的反思 prompt，或硬上限。

A2

上下文压缩丢约束

"summarize 后模型忘了 system prompt 说的事"

老消息被摘要后，关键约束（"不许动 /web"）被合并甚至省略。修复：把 system + 关键 rule 标 pinned，绝不参与压缩。

A3

Hook 误伤正常工作流

"白名单写错，连 README 都写不进去"

Hook 写得太严，每次都阻断；太松又拦不住真问题。修复：原则 = "宁漏判不误伤"，异常默认放行；stderr 给可执行的修正建议。

A4

Skill 套娃

"开了 12 个 skill，每次都被注入一大段，token 爆炸"

把"建议性提示"塞太多到 description。修复：skill 元信息只放路径 + 触发条件，正文懒加载（model 决定要读时再读）。

A5

隐式权限提升

"用户点同意一次 git push，agent 以为以后都能 push"

权限授予的作用域没讲清。修复：每次 risky 操作单独询问；记忆只保留"用户偏好节奏"而非"操作授权"。

§ 06

对 DeepInsight 的启示

放回我们自己项目语境，可行动的 4 条

启示 1

我们也需要自己的 harness

DeepInsight 的"分析洞察 agent"不是一次 prompt 调用 —— 拿到 PDF / 链接后要 chunk、要 retrieve、要画图、要留 citation。这一层就是我们自己的 harness。提前决定它的 5 大组件，比 UI 改 5 版更重要。

启示 2

把"看板 hooks"从插件做成产品

探索期已经在用 PreToolUse hook（check-explore-path.js）守路径。这种"用户能改、AI 必须遵守"的层，未来要不要在 DeepInsight 主应用里也开放？值得一个 spec。

启示 3

最小可演示报告 = 这一份本身

这份报告的呈现形态（左 TOC + 中正文 + 右元信息 + 雷达 + 矩阵 + 来源卡片）就是 DeepInsight 主应用第一个垂直切片可以瞄准的目标。沉到 docs/specs/ 当 reference。

启示 4

Skill 库做精不做多

反模式 A4 是真问题。.claude/skills/ 应控制在 5–7 个高频，每个有清晰触发条件，正文懒加载，避免 description 过长。

开放问题

Q1 · 我们的 harness 要不要走 Subagent 路线？
单一 long context vs. 多个隔离 subagent 是当前选择题。各有 tradeoff，需要 ADR 立场。
?
Q2 · 报告输出是 HTML 静态、Markdown、还是结构化 JSON + 渲染层？
影响下游 SEO / 收藏 / 分享形态，也影响离线/在线模式选择。
?
Q3 · 引用追溯做到哪个粒度？
句级 citation 工程量大、段级简单。MVP 先做哪一级？看用户认知阈值。
?
Q4 · 探索期 hook 那一套，要不要做成产品级 plugin 让用户自带？
"用户写规则、agent 守规则" 有差异化潜力，但 UI / 安全 / 性能成本未知。
