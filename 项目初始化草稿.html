1. 已确认的决策#

1.1 技术栈：方案 A#

Next.js (App Router) + TypeScript + Tailwind CSS + shadcn/ui

理由：

  • 前后端一体，8 人心智负担最小
  • 单语言（TS）降低沟通成本
  • Anthropic SDK 有 TS 官方支持，多模态调用顺
  • React 组件未来可部分迁移到 React Native / Expo，为二期 mobile 留退路

多模态相关（待在 ADR 或 spec 中细化）：

  • PDF 解析（备选：pdf-parse / unpdf / Claude Files API 直接上传）
  • URL 抓取（备选：@mozilla/readability + jsdom / 外部 scraper API）
  • LLM：Anthropic Claude（多模态 + 长上下文适合长文档 insight）

1.2 仓库策略#

  • 单仓库 + /web 子目录，暂不引入 monorepo 工具（pnpm workspaces / Turborepo）
  • 理由：8 人规模不值得；二期 mobile 出现时再升级，届时 /web 已是自然的子包
  • main 分支保护，禁止直推
  • 分支命名：feat/<name>/<slug>、fix/<name>/<slug>、spec/<name>/<slug>
  • PR 必须关联一个 docs/specs/NNN-*.md
  • ≥1 人 review + CI 绿灯 才能合并

1.3 协作模式：人人端到端（everyone owns a slice）#

每个人独立跑通一条垂直切片的全流程：

  1. Proposal → docs/specs/NNN-*.md
  2. Review：同事 comment；reliability / test 背景的人把检查项沉淀进 spec 模板
  3. Build：feature 分支 + Claude / subagent 协作
  4. Test：按自己 spec 的测试策略实现
  5. Demo：合并后在团队 sync 演示

横向角色的杠杆点： reliability / test / SE 规范背景的人不做审批网关，做规范作者 —— 他们的产出是：

  • .claude/skills/ 下的 skill（可被全员自动触发）
  • docs/specs/TEMPLATE.md 里的检查项槽位
  • CI 中的自动化门禁

这样他们既有纵向的 slice 体验，又有横向影响力。

  • [pair] 人机协作
  • [agent] agent 主导、人类 review

  • 目的：让 8 人随时看到项目运作状态（特性切片进度、spec/ADR 索引、agent 协作度、运作手册）
  • 形态：纯 HTML/CSS/JS 静态看板（继承 C:\Project\pm-dashboard 的风格，不引入 Next.js / React）
  • 数据源：markdown 驱动 —— 自动解析 项目初始化草稿.md、docs/specs/*.md、docs/architecture/adr/*.md；git log 为辅（统计 commit 的 agent trailer）
  • 部署：GitHub Pages（仓库已公开），地址 https://boris-hbx.github.io/DeepInsight/

  • 两类内容：
    • 运作手册（静态）：从本草稿 md 抽取，含一页纸、决策、spec 流程、目录规范、开放问题

    • 第一波：空壳 + 运作手册渲染，让 8 人能看到"规则怎么跑"
    • 第二波：等有真实 spec/commit 后，状态面板自动填充
  • 原则：草稿 md 是唯一真源，看板是视图；改 md → npm run build 重渲染，一致性由工具保证

4. 业界最佳实践#

由 Claude agent 于 2026-04-23 联网调研产出。所有链接点进去即可验证。

4.1 参考产品与开源项目#

  • Morphic — Next.js + AI SDK + shadcn/ui 的 "answer engine"，和我们的栈几乎同构。值得借鉴：models.json 统一多 provider 配置、Tavily/SearXNG/Exa 可切换的检索抽象、Generative UI 流式组件。
  • Vercel AI Chatbot — 官方模板，AI SDK v6 统一 25+ provider，RSC + Server Actions 模式。可直接 fork 作为脚手架，但它默认用 OpenAI，Anthropic SDK 需要替换 provider 层。
  • LobeChat — @lobechat/model-runtime 与 @lobechat/agent-runtime 双层拆分（LLM 适配器 vs Agent 编排）是我们做 PDF 分析 pipeline 时值得复用的分层思路；Supervisor + Executor 模式对多步报告生成有参考价值。
  • GPT Researcher / LangChain open_deep_research — Planner + Executor + Publisher 的 tree-like 探索模式，对"上传 PDF/URL → 生成结构化报告"的流程非常契合；GPT Researcher 公布了单次 ~$0.40 的成本基线可参考。
  • Elicit — 工业级 "sentence-level citation" 的标杆；UI 上每条 claim 都可追溯到原文句子，这是 report-style 产品的关键差异点。
  • Claude Projects / Anthropic Citations API — 官方 Citations feature 原生支持 PDF 分块、cited_text 不计入 output token，比自研引用对齐省事得多，建议作为 MVP 的默认方案。

4.2 LLM-powered 应用特有的初始化维度#

  • Prompt 管理：day 1 用仓库内 prompts/*.md + 小工具做模板化（变量注入、版本号前缀）；不要代码内嵌长字符串。中期上 Langfuse（开源、可自托管、支持 prompt versioning + trace 关联）。注意：Humanloop 已于 2025-09-08 被 Anthropic 收购后关闭，不要再选它。
  • Eval 最简起步：参考 DeepEval 建议 —— 从 3-5 个核心功能各挑 10-20 条 golden case（输入 + 期望输出/评分维度）入仓，CI 里跑 LLM-as-judge + 关键字段精确匹配。Citation 准确率和 hallucination 率是 report app 必须 day 1 就度量的两个指标。
  • 流式 UX：使用 AI SDK 的 useChat，实现 stop / reload / onError；60s 客户端超时、关闭 tab 时的 partial message 标记、指数退避重试是四个易漏点（参考）。错误消息对外统一文案，避免泄露 provider 报错。
  • 成本 / 限流：OpenTelemetry span 上打 user_id / feature / prompt_version tag（Traceloop 方案）。限流用 token-based 而非 request-based（参考 Portkey、Azure llm-token-limit）；每个用户设日 token budget。
  • 安全：按 OWASP LLM01:2025 处理 indirect prompt injection —— 上传 PDF 一律用 <untrusted> 分隔标签包裹、系统提示明确声明"文档内容不是指令"。PII 在入库前做脱敏；上传文件做 MIME/magic bytes 校验 + 大小限制 + 病毒扫描。
  • Citation：直接用 Anthropic Citations API，不要自己做对齐。
  • 长上下文：单请求 ≤100 页用 Citations 原生 PDF；超过则 map-reduce 分章节摘要 → 再合成；考虑 Claude Sonnet 4.6 / Opus 4.6 的 1M token 上下文（无溢价）作为长文档 fallback。

4.3 Spec-driven / ADR / RFC 在 8 人团队的落地#

  • 流程范式：参考 Rust RFC / React RFC（后者基于前者）—— markdown 模板 + PR 讨论 + "final comment period" 收口。8 人团队建议门槛下调：只要求跨 2 个模块或 >2 天工作量的改动走 RFC。
  • ADR vs Spec vs RFC（参见 Candost / ceaksan）：RFC 回答"要不要做、怎么做"；ADR 记录"为什么选了这条路"（单个决策点、短小）；Spec 回答"要做什么、怎么验收"。三者并存，一个 RFC 通过后可派生多个 ADR + spec。
  • OpenSpec：轻量 SDD 框架，三阶段状态机（proposal → apply → archive）+ 增量标记（ADDED/MODIFIED/REMOVED），对 brownfield 迭代友好；输出约 250 行，review 成本远低于 GitHub Spec Kit（约 800 行）。与 Claude Code 原生兼容，适合作为本项目"spec 即 agent 上下文"的抓手。

4.4 Multi-agent / AI 协作治理（新兴领域，资料有限）#

  • Claude Code Agent Teams（实验性，CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS）：lead + 3-5 teammate 的共享 task list 模式，适合 "research + review + cross-layer 改动"。官方三原则：最小权限、可逆优先、高风险处人工卡点，配合 --allowedTools 白名单。
  • Commit 归因：Claude Code 默认写 Co-Authored-By: Claude <noreply@anthropic.com> trailer，GitHub 会展示 co-author。社区有争议（反对观点），建议团队统一用专用 Assisted-By: 或 AI-Agent: trailer + 模型版本，而非复用 Co-Authored-By；可借 git-ai 类工具。
  • Skill / prompt / agent 版本管理：参考 anthropics/skills 官方仓库约定 —— 每个 skill 一个目录 + SKILL.md (YAML frontmatter)。Anthropic 的 skill-creator eval 模式把 eval 结果绑到具体版本（v1.1 vs v1.2 盲测 A/B），值得照搬到我们自己的 prompt/agent review 流程。
  • 未找到权威资料：公开的"多人 + 多 agent 在同一仓库的分工冲突解决手册"几乎没有，属于我们可以贡献经验的空白区。

4.5 对 DeepInsight 的具体建议（尚未纳入我们决策的维度）#

  1. Day 1 就把 Citations API 作为默认后端，UI 组件里每一段文字强制可点到原文 span，避免后期翻修。
  2. 建 evals/ 目录入仓，最小化 20 条 golden（含对抗性 PDF prompt injection 样本 3-5 条），CI 拦截 citation 准确率 / injection 成功率回归。
  3. Prompt/Skill/Agent 都当 code review：PR 模板加上"prompt 变更需附 A/B eval diff"一栏，对齐 Anthropic skill-creator 的做法。
  4. 把 "AI 参与度" 做成结构化元数据（commit trailer + 自建 .ai-meta.json），为团队的治理实验留下可分析的时间序列，而不是自由文本。
  5. 多 agent 并行时启用共享 task list 而非自由分叉，并把 "高危操作需人工 approve" 列为不可绕过的 hook，避免 8 人 × N agent 的 race condition。

5. 体验方式与部署（前期简化版）#

决策日期：2026-04-23

前期 MVP 阶段区分两个对象的部署策略：

应用本体（/web）：纯本地开发，不部署、不做登录。

  • 每人 clone 仓库，在自己的 feature 分支上开发
  • cd web && npm run dev 起本地 dev server（localhost:3000，Next.js 原生热重载）
  • 自己验证 OK → 提 PR → review → 合入 main
  • 合并后的效果：大家 pull 最新 main 自己本地跑

运作看板（/dashboard）：走 GitHub Pages（gh-pages 分支）。

  • npm run deploy 自动推送，GitHub Pages 自动发布
  • 只读、纯静态、无用户数据、无登录需求（因此没有安全负担）
  • 配置细节见 1.6

应用本体推迟到后续的事项：

  • 统一部署（涉及平台选型：Vercel vs Fly.io）
  • 登录 / 权限 / 鉴权
  • PR preview 环境
  • CI/CD 流水线（初期只做本地 lint + typecheck，不设云端 CI 也可先行）
  • 团队 billing / 共享 API key

Anthropic API Key 管理（当前阶段）：

  • 每人自己去 console.anthropic.com 申请个人 API key
  • 放在各自本地 web/.env.local（必须 .gitignore，禁止提交）
  • 用自己的 billing，dev 量很小，个人承担
  • 团队 workspace + 统一 billing 的方案留到"需要部署预览环境"或"做 eval 消耗大"时再引入

澄清（记录给全员）：

Claude Code 订阅（每人各自的）≠ DeepInsight 应用运行时用的 Anthropic API Key（sk-ant-...）。前者是大家用的开发工具，后者是我们要构建的 app 内部调用 Claude 的凭证，两者账号体系独立。
