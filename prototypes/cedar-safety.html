// 规则逐条详解
这道缰绳，一共就这几条
分三类：红线 forbid（撞上必拒，一票否决）、白名单 permit（默认拒绝，这里显式放行）、审批 approval（允许但要人点头）。每张卡：真实 Cedar 代码 → 人话翻译 → 撞它的例子 → 为什么有它。
这就是 spec 设计的 agent/policies/agent.cedar 文件的全部规则。Cedar 评估顺序固定：先查光所有 forbid → 再查 permit → 都没中就默认拒绝。所以任意一条 forbid 命中，permit 再多也救不回来——这就是「一票否决」。

// 策略在哪配置
一个纯文本文件，跟着仓库走
没有数据库、没有控制台。策略就是一个 .cedar 文本文件，改它 = 改文本，不动 Python 代码。

① 文件位置与结构

agent/
└─ policies/ 🔒 红线：agent 不可写
   ├─ agent.cedar # 全部规则
   └─ schema.cedarschema # 供 CI 校验

agent.cedar 里就是上面那几张卡的 Cedar 代码，顺序排下来。schema 声明有哪些实体/动作类型，CI 用它兜语法错。

② 它如何生效

  1. CedarPDP 启动时读 agent.cedar 的文本
  2. 每次危险动作前，构造 P/A/R/C 请求
  3. 丢给 cedarpy.is_authorized(request, policies)
  4. 引擎按 forbid→permit→默认拒绝 返回判定
  5. 改规则只需改这个文本文件，无需改代码
🔑 关键闭环：删掉缰绳 = 自我锁死，而不是获得自由

先讲清边界：人是信任根。你（被授权的人）想删，Cedar 不拦你也不该拦——你直接 rm 就行，不用通过 agent。Cedar 防的是 agent 自主地、或被注入内容驱使地改自己的缰绳，不是防你这个机主。

再讲真机制：那条 forbid.policy_or_secret_write 只在删除动作经过 PEP 时有效。子进程 os.remove() 直接 syscall 不经过 Cedar。所以真正兜底的不是那条规则，是这个性质——

😈 agent 删/改 agent.cedar→ 内存校验和不匹配→ PDP 进 deny-all-dangerous→ agent 失去一切危险权限 🔒

即「fail-closed-on-missing」：策略一旦消失/被改，不是放行，是全面锁死。前提有二：① 期望校验和的信任锚不能和策略文件放一起（否则一起删就绕过）——须编译进代码 / 宿主只读挂载；② 生成工具跑在沙箱里（无仓库写、策略只读）。这两条是 Phase 2 的硬前置，不是可选项。

⊘ shadow 模式（先上）

只判定 + 记录日志，不真拦。跑现有 workflow，收集「本会被拒的合法操作」→ 补 permit。零破坏地把策略调对。

● enforce 模式（调对后切）

真正阻断。一个配置开关切换，规则文件不用动。这是 spec 的 Phase 0 → Phase 1/2 路径。

// 关键：拒绝 ≠ 杀死
这才是「可控」的精髓
确定性闸门若只会「拒绝 + 崩溃」，agent 就废了。可控的意思是：把它圈进可行域里继续干活，而不是打死。

✗ 朴素做法 — 直接崩

1 agent 计划：建个用 subprocess 的工具
2 Cedar → DENY
3 raise PolicyDenied — 整个 run 崩溃 💥
4 任务失败，什么都没产出

✓ 本方案 — 拒绝即反馈

1 agent 计划：建个用 subprocess 的工具
2 Cedar → DENY + 原因 / 被允许的替代
3 DenialFeedback 回灌 _plan_task
4 agent 重规划 → 用现成安全工具 → 完成 ✓
声明式 pipeline（固定 DAG）保持 raise；只有会重规划的 AgentLoop 走「拒绝即反馈」，重规划上限 2 次，超限干净中止并说明原因。

// 每次都记？
log-or-deny —— 记不下，就不放行
你问「能否确保每次都记」。答案：把「必须记录」和「允许通过」焊死——判定返回之前先写审计；所有 sink 写失败 → 判定强制改成 DENY。于是"没有日志就没有动作"成了结构性不变式，不是尽力而为。点下面的开关，看 sink 故障时判定如何被翻成 DENY。
审计 sink：

✓ sink 正常 — 判定如实返回

1 Cedar 评估 → 原始判定（如 ALLOW）
2 build_record（含 seq / prev_hash / hash）
3 audit.write() → ≥1 sink 成功
4 返回原判定 → 动作放行 ✓ 且已留痕

三路冗余 sink

● agent/.audit/* 追加写 · agent 不可达
● stderr · 飞出进程即不可改
● 宿主侧 / off-box（可选）
⛓ 每条带 seq+hash 链：删/改任一条 → 校验报断点
不变式：经过 PDP 的每个判定，返回前必有一条记录；记不下 = 判定变 DENY = 无动作。shadow 模式不阻断也照记——记录无条件，执法才有条件。
⚠ 诚实边界：这只保证经过 PDP 的判定必记。子进程 os.remove 直接 syscall 没有判定可记——唯一真解仍是沙箱（spec 002）把操作收回受 PDP 中介。事后篡改：detect，非 prevent。
